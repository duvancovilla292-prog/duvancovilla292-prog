## 03 · Metodología: la partida

Programar es jugar con estructura, anticipación y precisión. Cada proyecto sigue tres fases.

<table>
<tr>
<th align="left">Fase</th>
<th align="left">Principio</th>
<th align="left">Aplicación</th>
</tr>
<tr>
<td><b>Apertura</b></td>
<td>Controlar el centro</td>
<td>Definir el modelo de datos y los contratos entre módulos antes de escribir la primera función.</td>
</tr>
<tr>
<td><b>Medio juego</b></td>
<td>Táctica y anticipación</td>
<td>Prever casos borde y fallos a varias jugadas de distancia. Iterar en pasos pequeños y reversibles.</td>
</tr>
<tr>
<td><b>Final</b></td>
<td>Precisión técnica</td>
<td>Pruebas, validación de entradas y despliegue sin margen de error: una pieza mal colocada decide la partida.</td>
</tr>
</table>

<details>
<summary><b>♟ Notación del flujo de trabajo</b></summary>
<br>

Mi ciclo de desarrollo, escrito como una partida:

```text
1. schema    ...  validar        # apertura: modelo y restricciones primero
2. feature   ...  test          # desarrollo con red de seguridad
3. refactor  ...  commit        # simplificar antes de avanzar
4. deploy+   ...  mate limpio   # entrega sin deuda técnica
```

> Un buen sacrificio de complejidad hoy evita perder material mañana.

</details>

## 04 · Rendimiento: leyes fundamentales

El código también obedece leyes. Optimizar es medir, no suponer.

<table>
<tr>
<th align="left">Principio</th>
<th align="left">Equivalente en ingeniería</th>
</tr>
<tr>
<td><b>Conservación de la energía</b></td>
<td>Los recursos no se crean: se gastan. Menos consultas, menos re-renders, menos memoria.</td>
</tr>
<tr>
<td><b>Mínima acción</b></td>
<td>De todas las soluciones posibles, la correcta recorre el camino más corto.</td>
</tr>
<tr>
<td><b>Entropía</b></td>
<td>Sin mantenimiento, el desorden crece. La refactorización es trabajo contra el caos.</td>
</tr>
<tr>
<td><b>Precisión numérica</b></td>
<td>Unidades coherentes, tipos explícitos y control del error acumulado.</td>
</tr>
</table>

<details>
<summary><b>∑ Notas de cálculo</b></summary>
<br>

```text
Complejidad objetivo      O(n log n) o mejor en rutas críticas
Criterio de optimización  medir primero → perfilar → mejorar el cuello de botella
Regla                     la optimización prematura es una fuente de error; la medición, de verdad
```

</details>

## 05 · Arquitectura de sistemas y gestión de datos

Cada sistema es un flujo de información: se ingiere, se analiza, se almacena y se responde. Una arquitectura limpia funciona como una mente ordenada.

<table>
<tr>
<th align="left">Habilidad</th>
<th align="left">Implementación</th>
</tr>
<tr>
<td><b>Análisis y evaluación</b></td>
<td>Modelado relacional y normalización hasta 3FN. Cada dato con su lugar y su relación.</td>
</tr>
<tr>
<td><b>Procesamiento en paralelo</b></td>
<td>Flujos asíncronos y agentes de IA coordinados con <code>n8n</code> + Gemini.</td>
</tr>
<tr>
<td><b>Ingesta de información</b></td>
<td>Entrada de datos desde Telegram, Sheets y APIs REST hacia un esquema validado.</td>
</tr>
<tr>
<td><b>Ley del sistema</b></td>
<td>Triggers y procedimientos almacenados: las reglas de negocio viven en la base de datos.</td>
</tr>
</table>

<details>
<summary><b>◈ Matriz de información · Gran Sabio</b></summary>
<br>

```text
 ENTRADA  ──►  ANÁLISIS  ──►  PERSISTENCIA  ──►  RESPUESTA
 Telegram      validación     MySQL · 3FN        mensaje / API
 Sheets        agente IA      Firebase RTDB      panel web
 REST          reglas         triggers           reporte
```

Los datos no se almacenan: se **analizan** antes de entrar y se **predicen** al salir.

</details>
